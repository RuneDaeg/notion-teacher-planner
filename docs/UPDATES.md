# 기존 교무수첩 업데이트

이미 사용 중인 Notion 수첩은 Git 저장소나 서버를 배포해도 같은 화면으로 자동 변경되지 않는다. 이 저장소는 **기존 수첩을 유지하면서 교사가 선택한 변경만 적용**하고, 수첩별로 적용 단계와 확인 시각을 기록한다. 전체 수첩을 다시 복제하거나 학생·상담 기록을 새 DB로 옮기는 절차가 아니다.

현재 업데이트 목록 버전은 **2026.10.1**, 첫 항목은 **학생별 상담 이력 연결 (`student-history-v1`)**이다. 목록의 버전과 각 항목의 적용 상태는 별개다. 목록이 최신이어도 모든 항목을 적용했다는 뜻은 아니다.

## 교사가 사용하는 순서

1. 수첩 홈의 **업데이트 확인**을 연다. 로그인 시간이 지났다면 기존 수첩의 Notion 연결을 다시 승인한다. 학교 정보나 NEIS 키를 새로 입력하지 않는다.
2. 변경 설명을 읽고 원하는 항목에서 **이 업데이트 적용**을 누른다. 적용 중에는 학생·상담 DB의 기록과 속성 편집을 잠시 멈춘다. 이미 등록한 항목은 **적용 상태 다시 확인**으로 진행 상태를 확인한다.
3. **AI와 확인 필요**라면 **AI에게 요청할 문장 복사**를 사용한다. 기존 상담이 있는 단방향 관계는 서버가 자동 전환하지 않는다. AI가 아래 보존 절차에 따라 기존 연결과 화면을 확인한다.
4. **관계 연결 확인 · 화면 설정 대기**가 되면 실제 Notion 학생 페이지를 연다. 해당 학생의 과거 상담이 보이고 `상담일` 내림차순인지 확인한다. 화면 구성이 없거나 정렬이 다르면 AI에게 설정을 맡긴다.
5. 확인한 뒤 관리 화면의 확인란을 선택하고 **화면 확인 완료 기록**을 누른다. 서버는 관계 구조를 다시 검사하고 화면을 확인했다는 교사의 응답을 기록한다. 서버가 Notion 화면·정렬을 직접 검증했다는 뜻은 아니다.

이전 수첩에 업데이트 링크가 없거나 적용 버튼이 비활성화되어 있으면 설치를 도운 AI에게 링크 추가를 요청한다. 학생·상담 DB 위치를 한 번 확인해야 하며 수첩을 새로 만들 필요는 없다. 일반 `/connect` 주소만으로는 최초 업데이트에 필요한 대상 ID가 전달되지 않는다.

```text
https://github.com/RuneDaeg/notion-teacher-planner 의 docs/UPDATES.md를 읽고
내 기존 교무수첩에 student-history-v1 업데이트를 적용해 줘.
기존 기록과 설치 상태를 유지하고, 정확한 DB·속성 ID와 적용 상태를 확인해 줘.
학생별 상담 보기와 상담일 내림차순 정렬까지 실제로 검증하고,
홈에 업데이트 확인 링크를 추가해 줘.
수첩 주소: [내 교무수첩 홈 주소]
```

## 첫 업데이트가 처리하는 범위

| 현재 구성 | 서버 동작 | 남은 확인 |
| --- | --- | --- |
| 학생·상담이 이미 올바른 양방향 관계 | 기존 속성 ID를 검증하고 적용 이력에 등록. 스키마를 다시 쓰지 않음 | 학생 페이지의 이력 보기·정렬 |
| 상담 DB가 비어 있고 학생 관계가 단방향 | 빈 상태와 속성 충돌 여부를 재검사한 뒤 양방향으로 전환 | 학생 페이지의 이력 보기·정렬 |
| 상담 기록이 있는 단방향 관계 | `assistance_required`로 보류. 기록이나 관계 값을 자동 변경하지 않음 | AI가 전체 관계를 보존하며 전환·검증 |
| 속성 이름 충돌·대상 변경·확정할 수 없는 쓰기 결과 | 재조회하거나 AI 확인 단계로 보류 | 정확한 기존 ID와 실제 변경 결과 확인 |

서버는 학생 본문, 상담 본문, 학생과 상담을 연결하는 관계 값, 공통 페이지 레이아웃을 쓰지 않는다. 빈 DB 전환 중 서버가 만든 역관계의 이름은 `상담 기록`으로 정리할 수 있지만, 사용자가 이미 쓰는 다른 속성을 같은 이름으로 교체하지 않는다. 편집자가 동시에 기록을 추가하지 않도록 적용 동안 관련 DB 편집을 멈춘다. Notion의 여러 변경을 하나의 트랜잭션으로 묶거나 전체 변경을 한 번에 되돌리는 기능은 없다.

| 저장 상태 | 화면 표시와 의미 |
| --- | --- |
| 미등록 (`available`) | 미적용. 해당 항목을 선택하기 전 |
| `pending` | 진행 중. 확정되지 않은 응답은 실제 상태를 다시 확인하고 이어서 처리 |
| `schema_applied` | 관계 연결 확인 · 화면 설정 대기. 상담 이력 화면까지 완료한 것은 아님 |
| `assistance_required` | AI와 확인 필요. 자동 변경을 보류한 이유 확인 |
| `complete` | 적용 완료 · 화면 확인 기록됨. 관계 검사와 교사의 화면 확인 기록이 있음 |

`complete`는 당시의 확인 기록이다. 이후 Notion에서 레이아웃을 바꿨는지 서버가 계속 감시하지 않는다. 서버 배포·일일 급식 갱신·수첩 구조 업데이트는 각각 별도로 동작하며, 업데이트 항목을 모든 교사의 수첩에 일괄 적용하거나 알림을 방송하지 않는다.

## 설치 AI: 기존 홈에 링크 한 번 추가하기

1. 원래 설치 경로의 상태와 클라우드 연결 manifest를 읽는다. MCP 상태를 Python 상태로 변환하거나 두 설치 경로를 합치지 않는다. 학교·루트·급식·상태·업무 일정의 **기존 manifest는 그대로** 유지한다.
2. 학생·상담 원본 data source와 상담 DB의 학생 관계를 실제로 조회한다. 데이터베이스 ID, data source ID, 페이지 ID, 속성 이름을 서로 대신 쓰지 않는다. 관계의 **속성 ID**와 대상 data source가 정확히 맞고 둘 다 승인한 수첩 아래인지 확인한다.
3. `.local/update-targets.json`을 준비한다. 실제 ID는 비공개 파일에만 저장한다.

```json
{
  "version": 1,
  "students_data_source_id": "실제 학생 원본 data source UUID",
  "counseling_data_source_id": "실제 상담 원본 data source UUID",
  "student_relation_property_id": "상담 DB 학생 관계의 실제 속성 ID"
}
```

저장소 루트에서 다음 명령을 실행한다. `https://planner.example.com`은 설명용이며 실제 배포가 확인된 서비스 주소로 바꾼다.

```bash
python -m teacher_planner.updates \
  --service-url https://planner.example.com \
  --manifest .local/cloud-manifest.json \
  --targets .local/update-targets.json \
  --output .local/update-link.json
```

4. 생성한 링크를 홈에 **업데이트 확인**이라는 이름으로 추가한다. 기존 자동 갱신 연결 링크·본문·메모를 유지하며, 같은 링크가 있으면 중복 삽입하지 않는다. 링크 생성은 업데이트 적용이나 클라우드 연결 완료가 아니다.
5. 링크를 열어 학교·수첩이 맞는지 확인한다. 링크에는 `{connection: 기존 manifest, updates: 대상 정보}`가 담긴다. manifest에 새 필드를 끼워 넣지 않으며 토큰·학생 이름·상담 내용을 넣지 않는다. 최초로 해당 항목을 적용할 때 정확한 대상과 진행 상태가 서버에 저장된다. 등록 후 다른 DB·속성 ID로 바꿔 같은 이력을 재사용하지 않는다.

클라우드 연결이 없는 교사도 아래 AI 절차로 해당 수첩을 수정할 수 있다. 이 경우 로컬 설치 기록에 결과를 남기되 서버의 적용 이력까지 등록됐다고 보고하지 않는다. Cloudflare 선택 업데이트 관리 화면을 이용하려면 실제 서비스와 기존 수첩의 OAuth 연결이 필요하다.

## AI: 기존 상담이 있는 수첩을 보존하며 적용하기

기존 기록이 있는 단방향 관계를 전환할 때는 다음 절차를 따른다. 교사의 업데이트 요청 범위에서 진행하되, 이미 사용 중인 관계를 삭제하고 다시 만드는 방식이나 이름으로 학생을 추정하는 방식은 사용하지 않는다.

1. 관련 DB 편집을 잠시 멈춘 상태에서 실제 스키마와 설치 상태를 읽는다. 상담 원본 data source, 학생 원본 data source, 기존 학생 관계 속성 ID를 저장한다. 이미 올바른 양방향이면 전환을 생략하고 양쪽 속성 ID·대상을 검증한다.
2. 모든 상담 페이지의 **페이지 ID와 전체 학생 관계 ID 배열**을 끝까지 조회해 `.local/`에 저장한다. 목록의 다음 페이지를 처리하고, 관계가 25개를 넘거나 `has_more`가 있으면 속성 항목 페이지까지 끝까지 읽는다. 첫 페이지의 관계 목록만 백업해서는 안 된다. 상담 본문·학생 이름·연락처를 이 백업에 수집하지 않는다.
3. 변경 전후 값·양쪽 속성 ID·진행 단계·확정되지 않은 요청을 비공개 작업 기록에 남긴다. 변경 직전 다시 확인한 스키마와 관계가 사전 기록과 다르면 멈춘다. 같은 이름의 다른 역관계나 변경된 속성을 덮어쓰지 않는다.
4. 기존 학생 관계를 양방향으로 전환하고 반환된 양쪽 속성 ID를 즉시 기록한다. 응답 유실·시간 초과 때는 재생성하지 말고 실제 스키마와 작업 기록을 먼저 비교한다. 스키마 성공만으로 관계 값이 보존됐다고 가정하지 않는다.
5. 모든 기존 상담의 관계 ID 배열을 다시 읽어 비교한다. 누락 복원은 사전 배열이 완전하고 해당 변경으로 생긴 누락임이 확인된 경우에만 같은 ID 배열로 진행한다. 다른 편집자의 변경, 새 연결, 원인 불명 차이가 있으면 자동 복원하지 않는다. 자료를 보존하고 확인이 필요한 기록만 알린다. 본문·관계 없는 속성·기존 학생 페이지는 유지한다.
6. [MCP 설치 안내](INSTALL_WITH_MCP.md)의 학생 DB 공통 `page_layout` 관계 보기를 사용하거나 실제 Notion UI의 레이아웃 사용자 지정으로 이력을 구성한다. 기존 본문·제목·토론·사이드바·다른 모듈을 유지한다. 전체 레이아웃을 보내야 하는 도구는 현재 구성을 먼저 읽어 필요한 관계 보기만 추가한다.
7. 필터는 해당 학생과의 관계, 즉 **이 페이지**를 기준으로 만든다. 특정 예시 학생 ID를 고정하지 않는다. 이 누적 이력에 오늘·최근 날짜·현재 학년도·보관 여부 제한을 추가하지 않는다. `상담일` **내림차순** 정렬을 설정하고 모두에게 적용되는 구성을 실제로 확인한다.
8. 상담이 있는 학생과 없는 학생, 다른 학생의 페이지에서 이력 구분·정렬·기존 본문 보존을 확인한다. 기록 수와 관계 ID 배열도 사전 자료와 비교한다. 실제 기록을 검증용으로 수정하거나 가상 상담을 끼워 넣지 않는다.
9. 관리 화면에서 **적용 상태 다시 확인**으로 관계를 재검증한다. 교사가 실제 학생 화면을 확인한 뒤 **화면 확인 완료 기록**을 누르도록 안내한다. 서버에 `schema_applied`만 남아 있으면 관계는 확인됐으나 화면 확인 기록은 대기 중이라고 구분해 보고한다.

Python 설치에서 설계 지문이 달라 `install`이 중단돼도 상태 파일을 삭제하거나 지문을 우회하지 않는다. 이번 변경은 위 선택 업데이트 절차로 적용한다. 원래 설치 상태와 별도로 해당 변경의 정확한 대상·결과만 기록하며, 전체 수첩을 새로 만들 필요가 있는 변경은 별도로 범위를 결정한다.

## 운영자: 새 업데이트 배포

Cloudflare의 `0002_template_updates.sql`을 적용한 뒤 업데이트를 지원하는 Worker와 연결 화면을 함께 배포한다. 기존 D1 데이터·암호화 키·manifest를 유지한다. [Cloudflare 배포 안내](CLOUDFLARE.md)를 따른다.

업데이트 이력은 일일 급식·학사일정 상태와 분리돼 저장된다. 같은 수첩의 변경은 기존 실행 잠금을 공유하며, 업데이트 요청이 하루 갱신 완료 시각이나 다음 실행 일정을 바꾸지 않는다. 일일 갱신이 일시 중지된 수첩도 연결이 유효하면 교사가 선택한 업데이트를 적용할 수 있다.

다음 항목을 추가할 때는 별도 업데이트 ID·설명·대상 검증·재시도 검증을 준비하고 필요한 D1 마이그레이션과 안내서를 함께 갱신한다. 기존 항목의 ID를 재사용해 다른 변경을 배포하지 않는다. 이미 배포된 서비스를 고치는 것만으로 이전 교사의 Notion 본문·레이아웃이 일괄 수정되지는 않는다.
