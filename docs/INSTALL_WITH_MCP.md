# Notion MCP/커넥터로 네 페이지 수첩 설치하기

이 경로는 AI에 연결된 Notion 쓰기 도구로 수첩을 구성한다. 기본 설치에는 별도 웹 앱이나 새로운 계정 서비스가 필요하지 않다. 요청받은 매일 자동 갱신은 아래 클라우드 등록을 별도로 진행한다. 도구가 읽기 전용이면 실제 생성 완료로 보고하지 않고 가능한 쓰기 경로를 안내한다.

## 준비와 설계 원본

1. `START_HERE.md`와 [공통 질문지](ONBOARDING.md)에 따라 이미 받은 학년도·반·교과·선택 모듈과 상위 페이지를 확인한다. 새 설치에서 수첩 전체의 학기는 묻지 않는다. 누락된 답만 고정 문구·순서·분기 규칙으로 받고 같은 답을 다시 묻지 않는다.
2. 연결 계정과 사용자가 지정한 상위 일반 페이지를 확인한다. 기존 설치가 있으면 그 기록을 먼저 읽는다.
3. 실제 도구의 enhanced Markdown·뷰 DSL·블록 명세를 읽는다. REST 요청 형식과 MCP DSL을 섞지 않는다.
4. `DESIGN.md`, `docs/DEFAULT_TEMPLATE.md`, `teacher_planner/dashboard.json` 버전 5의 `workspace.pages`, `teacher_planner/blueprint.json`, `teacher_planner/layout_contract.json`의 `teacher-desk-layout-v1`을 읽는다. dashboard는 논리 섹션, layout_contract는 실제 행·열·폭·접기의 기준이며 둘 다 따른다.

로컬 실행이 가능하면 `python -m teacher_planner plan --config .local/config.json --full`과 `python -m teacher_planner layout-plan --config .local/config.json`으로 선택 모듈에 따른 기능·배치 명세를 확인한다. `database_id`, `data_source_id`, `page_id`, `view_id`와 화면·섹션별 연결 DB ID를 각각 저장한다. MCP 기록은 `.local/mcp-install.json` 등에 보관하고 Python 상태와 섞지 않는다.

[공통 렌더러 사용법](DEFAULT_TEMPLATE.md#같은-배치를-출력하는-렌더러)을 따라 실제 네이티브 섹션 조각을 `render-layout --page ... --sections ... --output ...`으로 조합할 수 있다. 원본·연결 DB·페이지·동기화 블록을 먼저 전부 목록화하고 실제 태그·URL을 유지한다. 생성 파일을 기존 페이지 전체에 맹목적으로 덮어쓰거나 누락된 자식 페이지를 삭제하도록 허용하지 않는다. 렌더링과 Notion 반영·실제 화면 확인은 별도 단계다.

## 생성 순서

1. 상위 페이지 아래 `{academic_year}학년도 · {title}` 형식의 루트 대시보드와 `학급 경영 & 학생 상담`, `교과 진도표 & 시간표`, `학사 캘린더 & PARA` 페이지를 만든다. 학년도마다 한 권을 해당 연도 3월부터 다음 해 2월까지 사용한다. 네 핵심 페이지 모두 전체 너비를 켜고 작은 텍스트를 끈다. 문서화된 도구 설정이 없으면 각 페이지의 실제 `•••` 메뉴에서 적용한다. 원본 DB용 `운영 자료`, `학생 기록`도 같은 수첩 안에 두되 자식 페이지 목록은 홈 하단 문서 보관실에 정리한다.
2. 선택한 원본 DB를 만들고 반환된 data source ID로 관계를 연결한다. 기존 자료를 새로 복사하지 않는다. 전화번호·이메일·수식·갤러리 등은 실제 도구가 지원하는 정확한 유형으로 작성한다.
3. 담당 반·교과·영역을 넣고 원본 뷰를 만든다. `학년도`, `보관`, 날짜·상태 필터는 blueprint를 그대로 따른다. 데모를 요청하지 않았다면 실학생이나 가상 학생 기록을 넣지 않는다.
4. 네 페이지에 같은 실제 이동 링크를 만들고 `layout-plan`에서 해석한 각 행·열의 순서·폭·접기 구조를 먼저 구성한다. [고정 배치 표](DEFAULT_TEMPLATE.md#필수-공통-배치-계약)를 따라 실제 제목과 연결 DB를 같은 열 안에 넣는다. 홈 빠른 실행은 아이콘 콜아웃 4열이고, 중식/할 일·마감은 40/60, 출결/상담은 50/50, 진도/평가는 55/45다. 선택하지 않은 섹션만 생략하고 남은 열의 폭을 정규화한다.
5. 각 섹션의 첫 뷰로 연결 DB를 만든 뒤 같은 섹션의 후속 뷰를 그 DB의 보기 탭으로 추가한다. 선택하지 않은 모듈의 빈 섹션·링크는 만들지 않는다.
6. 홈과 교과 페이지의 기본 시간표는 세로 교시·수업 시간, 가로 월~금의 주간 격자로 만들고 같은 원본과 같은 표시 주간을 사용한다. 교과 페이지에 표시 주간 안내·격자·동기화 안내를 담은 원본 `synced_block`을 만들고 홈의 `오늘의 수업 · 주간 시간표`에는 그 참조를 둔다. 원본 관리 보기와 오늘·변경 목록은 주간표 아래 관리용 `details` 접기 영역으로 분리한다. 홈의 기존 오늘 수업 컨테이너는 `오늘 수업 원본 · 목록으로 확인` 같은 관리용 제목으로 보존한다. 접기는 설치 종료 시 닫힌 상태여야 한다. 도구만으로 구성할 수 없으면 UI로 보완하고, 보완하지 못하면 배치 확인 대기로 남긴다. 학급 페이지의 조회·종례 메모는 빈 수동 영역으로 둔다. 학생 사진·연락처·요약 숫자를 참고 이미지에서 가져오지 않는다.
7. 생성된 실제 원본·부모·탭·필터와 네 페이지 전체 블록 트리를 다시 조회한다. [ACCEPTANCE.md](ACCEPTANCE.md)의 필수 화면 증거를 모아 기능 설치·배치 재현·선택 연동을 각각 검증한다. 생성 응답의 ID 목록이나 DB 수만 맞는 것으로 화면 설치를 완료 처리하지 않는다.

모든 현재 학년도 뷰에는 설정 학년도와 `보관=false`, 보관함에는 해당 학년도와 `보관=true`를 적용한다. 학생 명렬표·학생 카드·관찰 학생, 출결 오늘·확인 필요·전체, 진도 반·교과·학기·보강 필요는 각각 같은 원본의 탭이다. 개인 정보가 있는 표를 숨기는 것만으로 권한이 분리되었다고 설명하지 않는다.

2학기에도 같은 수첩과 학생·상담·업무 원본을 사용한다. 수업 진도의 `학기`는 필요한 기록에서 선택하고 1·2학기 보기를 유지한다. 제목에 학기가 남아 있는 기존 수첩도 이어 쓸 수 있으며, 제목 변경을 요청받은 경우에는 기존 페이지 제목만 바꾼다. 제목 변경은 DB 구조 변경이 아니다. 학기 전환이나 제목 변경을 위해 수첩·기록을 복제하거나 원래 설정·설치 상태를 초기화하지 않는다. 기존 설정의 `semester`도 그대로 보존한다.

## 배치 쓰기 직후 다시 읽기

MCP가 기존 네이티브 블록을 보존하면서 페이지 본문을 적용할 때 입력 순서와 실제 블록 순서가 달라질 수 있다. **매번 쓰기 직후 전체 페이지를 새로 조회**해 계약의 부모·순서·열·접기와 대조한다. 차이가 있으면 현재 응답을 기준으로 문제 구역만 이동하거나 지원되는 부분 수정으로 고치고 다시 조회한다. 성공 응답만 믿거나 같은 전체 본문 교체를 반복하지 않는다.

급식·상태 콜아웃, 공유 시간표의 동기화 원본/참조, 표·표시 주간 문단·각 교시 행의 실제 ID와 부모를 수정 전후 대조한다. 설치 기록이 오래된 ID를 가리키면 동기화 완료로 보고하지 않는다. **OAuth 등록 전인 새 수첩**에서 MCP 재구성으로 급식/상태 ID가 바뀌었다면 활성 블록을 다시 검증하고 비공개 설치 기록·연결 manifest·연결 링크를 갱신한 뒤 승인 절차를 진행한다. **이미 자동 갱신에 연결된 수첩**은 기존 급식·상태 블록과 ID를 보존하며, 이동 때문에 새 블록을 만들어 서버 연결을 임의로 바꾸지 않는다. 예상 밖 ID 변경은 실제 연결 대상과 기록을 확인해 복구·지원 절차로 처리하고 해결 전 연동 확인 대기로 남긴다.

## 학생 페이지에 누적 상담 이력 연결

학생별 과거 상담 이력은 현재 학년도 대시보드 보기와 구분한다. `상담 기록.학생`을 양방향 관계로 두고 학생 명단의 역관계 이름을 `상담 기록`으로 사용한다. 새 상담에서 학생을 선택하면 그 학생 페이지의 관계와 이력 보기에 같은 원본이 나타나는 구조다.

1. 학생·상담의 실제 원본 data source와 기존 `학생` 관계, 대상 학생·상담의 연결을 읽는다. **기존 관계를 전환하기 전에 모든 상담 페이지 ID와 전체 학생 관계 ID 배열을 비공개로 저장한다.** 목록·관계 응답이 나뉘면 끝까지 조회하며 일부 행만 저장한 상태에서 전환하지 않는다. 기존 학생 DB에 `상담 기록` 속성이 있다면 같은 동기화 관계인지 확인한다. 같은 이름의 별도 관계를 만들어 대체하지 않는다.
2. 새 설치에서는 양방향 관계를 생성한다. 기존 수첩 변경을 요청받았다면 현재 `학생` 관계를 양방향으로 전환하고 학생 쪽 `상담 기록`과 연결한다. 스키마 변경 성공만으로 관계 값 보존을 가정하지 않는다. 반환된 양쪽 속성 ID·대상 data source와 모든 기존 연결을 다시 확인하고, 연결이 빠졌다면 **사전 저장한 해당 상담의 학생 ID 배열만 그대로 복원**한 뒤 양쪽에서 재검증한다. 이름·제목으로 새 연결을 추정하지 않으며 사전 값이 확인되지 않으면 복원을 중단한다. 기존 상담 원본·학생 본문·다른 속성은 유지한다.
3. 실제 도구가 지원하는 학생 DB 공통 `page_layout`의 관계 보기(`views`의 `relation="상담 기록"`) 또는 Notion UI의 레이아웃 사용자 지정을 사용한다. 특정 학생 ID를 고정한 필터 대신 현재 학생의 관계를 기준으로 표시하고 모든 학생 페이지에 적용한다. 기존 본문·레이아웃 모듈·다른 보기 설정은 보존한다.
4. 이 누적 이력에는 오늘·최근 날짜·현재 학년도나 보관 여부의 추가 제한을 자동으로 넣지 않는다. `상담일` 날짜순 정렬을 지원하면 설정한 뒤 다시 읽어 확인한다. 도구가 정렬을 지원하지 않으면 날짜순으로 완료했다고 보고하지 않는다. 기존 명렬표·상담 DB의 다른 보기 필터는 바꾸지 않는다.
5. 연결된 과거 상담이 있는 학생과 다른 학생의 페이지를 각각 열어, 해당 학생의 원본만 표시되는지 확인한다. 새로 연결한 상담도 같은 관계로 표시되는지 확인하고 원본 수가 늘지 않았는지 검증한다. 테스트를 위해 실제 상담 내용을 만들어 넣지 않는다.

학생을 선택하지 않은 상담은 이름·본문만으로 귀속시키지 않는다. 연결 누락은 실제 학생·학급·학생 ID를 확인해 보완한다. 기존 설치의 Python 상태를 초기화하거나 재설치로 변환하지 않는다. 새 Python REST 설치는 양방향 관계 속성까지만 구성하므로, 이 경로에서는 공통 페이지 레이아웃과 날짜순 목록을 별도 MCP/UI 작업으로 구분해 인계한다.

## 같은 섹션의 보기 탭 만들기

REST를 사용하는 경우 다음 순서로 만든다. MCP에서는 기존 연결 DB에 뷰를 추가하는 실제 도구 명세를 확인해 같은 구조를 만든다.

1. 첫 뷰에 원본 `data_source_id`와 대상 페이지의 `create_database.parent.page_id`를 지정한다.
2. 성공 응답의 `parent.database_id`를 **그 페이지·섹션의 연결 DB ID**로 저장한다.
3. 다음 뷰는 같은 원본 `data_source_id`와 저장한 연결 DB `database_id`로 생성한다. 이 요청에는 `create_database`를 넣지 않는다.
4. 같은 섹션의 모든 뷰가 같은 부모 DB와 원본을 사용하는지 확인한다. 다른 페이지의 동명 섹션은 별도의 연결 블록을 사용한다.

대시보드 캘린더는 `주간 캘린더 / 월간 캘린더` 탭을 갖는다. 둘 다 업무·일정 원본의 `일정` 속성을 사용하고 `configuration.view_range`만 week/month로 다르다. 학사 캘린더 페이지도 같은 원본으로 주간·월간 탭을 만들고, `마감` 속성을 사용하는 마감 탭을 같은 연결 DB에 추가한다.

주간·월간은 이름만 바꾸지 않는다. MCP DSL에서 실제 표시 범위를 지원하지 않으면 Notion UI 또는 지원하는 REST 뷰 설정을 사용하고 남은 작업을 명시한다. `WEEK` 같은 지원되지 않는 DSL을 추정해서 쓰지 않는다.

홈과 교과 페이지의 요일×교시 격자는 같은 교사 시간표 원본의 같은 주를 보여 주는 표시용 표다. 원본 DB와 `수업 시간표`·`변경·휴강` 목록형 보기는 격자 아래 `시간표 원본 · 관리용` 제목으로 구분한다. 문서화된 `details` 접기 구문 또는 실제 UI로 관리 영역을 만들고 기본 닫힘을 확인한다. Python REST로 직접 배치된 관리 목록도 같은 구조로 옮겨야 배치 확인을 통과한다. 미지원 상태를 대체 배치 완료로 보고하지 않는다. `오늘 수업` 관리용 보기는 같은 원본에 `오늘 수업=true` 수식 필터를 적용하고 교시 오름차순으로 표시한다. 기본·오늘·변경 관리 보기의 핵심 열은 `이름·수업일·교시·학급·교과·교실·상태`다. 수업을 업무·일정·To-Do·학사 캘린더에 복사하지 않는다. 기존 `업무·일정` 관계 속성은 유지하되 자동 연결·수리·해제하지 않으며, 이전 복사 일정도 자동 수정·삭제하지 않는다.

UI로 범위를 설정할 때는 대상 보기의 `설정 → 레이아웃 → 캘린더 표시`에서 주간은 `주`, 월간은 `월`인지 확인한다. 메뉴 이름은 실제 화면을 따른다. 원본 DB의 주간 보기와 각 페이지의 연결 주간 보기는 별도 설정이므로 모두 확인한다. `CALENDAR BY` 적용 성공이나 `주간`이라는 보기 이름만으로 범위 검증을 끝내지 않는다. 특정 주의 고정 날짜 필터를 추가하는 것은 주간 표시 설정을 대신하지 않는다.

## Notion 네이티브 배치와 동작

공통 배치 계약은 어느 설치 경로에도 동일하다. 전체 너비 켜기·작은 텍스트 끄기, 실제 열 비율, 홈의 다단 표와 하단 문서 보관실, 관리용 목록의 닫힌 접기는 선택 사항이 아니다. 사용할 수 있는 기능을 먼저 확인하고 지원되는 도구와 UI로 완성한다. REST가 만든 페이지 직속 연결 DB를 그대로 두고 모든 섹션을 세로로 쌓는 것은 기능 설치의 중간 결과다.

MCP의 열·접기·연결 DB 구문은 **발견한 도구의 문서**를 따른다. `full_width`, 비율, 기본 닫힘 같은 계약 값을 지원되지 않는 API 필드로 추측해 보내지 않는다. 구조를 쓰고 바로 다시 읽어 실제 부모·자식·형제 순서를 확인한다. 비율이 도구 응답에 없으면 데스크톱 실제 화면에서 열의 경계를 비교해 계약의 허용오차 안으로 조정한다. 제목·링크만 놓은 상태를 실제 데이터 표로 보고하지 않는다.

네 핵심 페이지의 `•••` 메뉴에서 전체 너비 켜기와 작은 텍스트 끄기를 각각 확인하고 증거를 남긴다. 창 폭과 줌을 함께 기록하며, 모바일에서 열이 세로로 쌓이는 반응형 표시는 데스크톱 설치 배치의 실패와 구분한다. 화면 검증 후 관리용 접기와 원본 링크 접기를 닫고 최종 상태를 캡처한다. 새로 진입한 화면에서도 기본적으로 닫혀 있는지 확인한다. 가능한 범위까지만 적용한 경우 구체적인 페이지·행·남은 설정을 배치 확인 대기로 남긴다.

2026-09-28 예시 설치에서는 페이지 배치에 `<database url="기존 연결 DB URL">표시 제목</database>`를 사용했을 때 연결된 원본 DB 이름까지 바뀌는 현상을 확인했다. 연결 DB를 재배치할 때 태그 안의 제목은 기존 원본 이름을 유지하거나 비워 두고, 화면별 섹션 이름은 별도 제목 블록으로 표시한다. 적용 후 원본 DB 이름을 다시 조회해 의도하지 않은 이름 변경이 없는지 확인한다.

요청된 HEX 색상·서체·화면 픽셀·240px 사이드바는 `DESIGN.md`의 참고 기준이다. 네이티브 제목, 회색 설명, 상태별 색, 콜아웃과 기본 사이드바를 사용한다. 정확한 CSS나 고정 사이드바를 설치했다고 안내하지 않는다. 네 핵심 페이지의 전체 너비와 작은 텍스트 설정은 필수이며, 열 폭 비율은 공통 배치 계약을 따르고 실제 UI에서 확인한다.

빠른 실행은 생성한 DB를 여는 링크다. 새 기록은 Notion의 새로 만들기를 이용한다. 사용자가 상태·확인·태그를 편집하면 그 원본 기록에 반영되는 기본 동작을 사용한다. 자동 업로드·성공 토스트·외부 알림을 가장하지 않는다. 숫자 집계가 필요하면 실제 지원되는 UI에서 개수·평균 계산을 설정하고 결과를 확인한다.

학교 공유 페이지·설문·NEIS·에듀파인 주소는 `dashboard.links`에서 입력한 선택형 바로가기다. 비어 있으면 설정 안내를 표시하고 실제 학교 주소를 추정하지 않는다. 링크를 로그인이나 데이터 동기화 연결로 설명하지 않는다.

PARA 콜아웃 네 열은 프로젝트·담당 영역·자료·보관함으로 연결한다. 프로젝트 상태 보드는 프로젝트 DB의 상태를 관리한다. 모든 PARA 항목을 드래그 한 번으로 서로 다른 DB 사이에 이동시키는 기능은 제공하지 않는다.

## 가져온 학사일정과 To-Do 분리

`우선순위 To Do`의 원본 보기와 홈 연결 보기에는 `외부 ID`가 `neis:`를 **포함하지 않음** 조건을 적용한다. 이 저장소의 NEIS 연동용 외부 ID를 기준으로 가져온 학사일정을 제외하며, 새 수식 속성은 만들지 않는다. 기존 보관·상태·학년도 조건과 정렬을 유지하고 수동 행사·업무는 계속 표시한다. 주간·월간 학사 캘린더의 필터는 바꾸지 않는다.

1. 원본 `우선순위 To Do`와 홈의 해당 연결 보기를 각각 조회해 현재 필터를 확인한다.
2. MCP DSL에 `NOT` 또는 문자열의 `포함하지 않음` 연산자가 없으면 Notion UI에서 `외부 ID → 포함하지 않음 → neis:` 조건을 기존 최상위 AND에 추가한다. `!= "neis:"`는 문자열 전체의 불일치이고 `STARTS WITH`는 포함 조건이므로 대신 사용하지 않는다.
3. 각 보기를 다시 `fetch`해 `외부 ID`의 문자열 필터가 실제로 `포함하지 않음`, 값 `neis:`로 저장되었는지 확인한다. 반환 연산자 이름은 사용하는 도구의 응답 구조를 따르며, 조건이 없거나 반대로 적용되면 완료로 처리하지 않는다.
4. 가져온 학사일정은 To-Do에서 빠지고 일반 수동 행사·업무는 기존 조건에 따라 남는지 확인한다. 같은 학사일정은 주간·월간 캘린더에서 유지되는지 확인하고, 후속 DSL 수정에서도 UI로 적용한 조건을 보존한다.

## 수식과 메모

오늘 수업·상담·출결은 원본 날짜와 오늘 날짜를 비교하는 수식·필터를 사용한다. 마감과 평가 D-Day는 원본 날짜로 계산하며 빈 날짜나 완료·취소 기록을 예정 업무로 표시하지 않는다. 학생 관찰 태그와 집중 관찰 체크는 실제 학생 원본에 저장한다. 조회·종례 콜아웃 메모는 수동 영역이며 자동 날짜 기록·복사·초기화가 없다.

### MCP 수식 필터의 실제 적용 확인

2026-09-28 예시 설치에서 `configure`에 `FILTER "오늘 수업" = TRUE`를 넣은 뷰 생성이 성공했지만, 다시 조회한 `advancedFilter`에는 해당 수식 조건이 누락된 사례를 확인했다. 모든 커넥터·버전에서 같은 결과가 난다는 뜻은 아니다. 성공 응답과 별개로 사용하는 도구에서 실제 적용 결과를 검사한다.

1. 원본 뷰와 연결 뷰를 각각 `fetch`해 `오늘 수업`, `오늘 상담`, `오늘 출결`, `지연`, `마감 임박`, `평가 예정` 중 설계에 필요한 수식 조건이 있는지 확인한다. 뷰 이름이나 화면에 보이는 행 개수만으로 판단하지 않는다.
2. 조건이 빠졌다면 해당 보기의 Notion UI에서 `필터 → 규칙 → 필터 규칙 추가`로 원래 수식 속성을 선택한다. **속성 선택 후 `값 선택 → 체크 표시됨`까지 지정**한다. 속성만 선택해 값이 비어 있는 상태는 완료로 보지 않는다. 기존 학년도·보관·상태 조건과 AND/OR 구조를 유지하며, 필요한 조건을 최상위 AND에 추가한다.
3. 다시 `fetch`해 해당 수식 조건의 `propertyType: "formula"`, `resultFilter.operator: "checkbox_is"`, `resultFilter.value.value: true`를 확인한다. `value`가 `{ "type": "exact" }`처럼 실제 값 없이 반환되면 미완료다. 응답 구조가 달라진 도구에서는 문서와 UI를 함께 확인해 같은 참 조건인지 검증한다.
4. 실제 원본 날짜·상태가 조건을 만족하는 행과 만족하지 않는 행의 표시를 확인하고 뷰별 검증 결과를 비공개 설치 기록에 남긴다. 동적 수식 조건을 고정 날짜 필터로 바꾸거나, 조건이 빠진 보기를 검증 완료로 보고하지 않는다.

UI로 보완한 뒤 필터를 지우고 동일한 DSL을 재적용하면 보완 내용이 사라질 수 있다. 이후 수정에서도 이미 적용된 수식 조건을 먼저 읽고 보존한다.

MCP로 만든 시간표 격자는 Python 설치 상태와 자동 연결되지 않는다. 파일·컴시간 수업을 반영하는 MCP 담당자는 날짜가 검증된 수업을 교사 시간표 원본에 기록한 뒤 해당 주 원본을 다시 읽어 공유 원본 안의 격자와 표시 주간 안내를 갱신하고 두 페이지 표시가 일치하는지 검증한다. 격자·표시 주간 안내 ID는 각각 하나만 기록하며 `synced_block` 객체 자체를 수정하지 않고 그 자식 블록을 갱신한다. 공유 표의 수동 변경이 다른 페이지에도 보이더라도 원본 DB에 역전송된 것으로 안내하지 않는다. 실학교와 연결하지 않은 새 설치는 빈 격자를 사용하며, 요청받은 가상 예시를 넣었다면 가상 데이터임을 표시한다. 공식 NEIS 출결·학적 쓰기, 컴시간 푸시, 자동 메시지 발송은 구현되어 있지 않다. 공개 학사일정 API 조회와 Notion 일정 반영은 별도 [SCHOOL_CALENDAR.md](SCHOOL_CALENDAR.md)를 따른다. 클라우드 매일 갱신은 아래 별도 등록과 배포가 필요하며, MCP 설치만으로 시작하지 않는다. Python 동기화에는 Python 설치 상태가 필요하므로 MCP 설치 ID를 임의로 섞지 않는다.

## 연속 학사일정의 기간 페이지

`neis-calendar`의 일자별 원본과 수첩 설정을 `teacher_planner.school_calendar.grouped_schedule(snapshot, config)`로 검증·그룹화한 뒤 기존 업무·일정 원본에 반영한다. 같은 교육청·학교·학년도·학교과정·주야과정과 같은 이름의 행사가 달력상 하루씩 이어져야 한 그룹이다. 중간 날짜가 없으면 별도 행사이며 주말·공휴일을 추정해 채우지 않는다. 그룹의 첫날과 마지막 날을 포함하는 종일 날짜 범위를 `일정`에 저장한다. 하루짜리는 종료일을 비운다. `source_rows`의 날짜별 설명·대상 학년·휴업 구분은 연동 전용 영역에 보존한다.

기존 날짜별 페이지의 통합을 요청받았다면 다음 순서로 처리한다.

1. 같은 학교·학년도의 3월 1일~다음 해 2월 말 전체 조회 결과와 기존 설치 기록을 읽고, 외부 ID에 해당하는 실제 페이지·본문·관계를 확인한다. 부분 기간으로 기존 원본을 처음 통합하지 않는다. API 결과가 여러 페이지면 끝까지 확인하고 전체 건수를 첫 페이지만으로 판단하지 않는다.
2. 이미 기록한 대표 페이지를 우선 재사용한다. 처음 묶는 그룹은 보관하지 않은 기존 페이지 중 가장 이른 일자를 대표로 선택하고 기간과 연동 전용 내용만 갱신한다. 모두 보관되어 있으면 가장 이른 원본을 사용하되 보관 상태를 유지한다. `source_ids`·대표 페이지 ID·원본 페이지 링크를 비공개 MCP 설치 상태에 보존한다.
3. 그룹에 속한 나머지 가져온 페이지에는 `보관=true`만 적용한다. 페이지 삭제·휴지통 이동·본문 재생성·관계 이동은 하지 않는다. 대표 페이지에 원본 링크를 남겨 기존 메모와 관계를 열어 볼 수 있게 한다. 교사가 직접 만든 일정은 이 통합 대상이 아니다.
4. 대표 페이지의 날짜 범위·본문을 다시 조회하고 원본 페이지의 보관 상태·메모 보존을 확인한다. 주간·월간 캘린더에서 대표 한 건이 기간으로 표시되며 To-Do 제외 조건은 유지되는지 확인한다.

후속 갱신은 저장한 일자 소속과 겹치는 그룹을 찾아 같은 대표 페이지를 사용한다. 첫날이 앞당겨지거나 종료일이 늘어났다는 이유로 새 페이지를 만들지 않는다. 저장된 기간을 자르는 부분 조회, 기간 축소·분리, 기존 두 그룹을 연결하는 변화는 자동 적용하지 말고 원본과 설치 기록을 비교한다. 이름 변경·겹침 없는 날짜 이동·누락은 [재조회 규칙](SCHOOL_CALENDAR.md#같은-행사를-다시-조회할-때)을 따른다. 기존 MCP ID를 Python 상태에 넣거나 `neis-sync --apply`로 우회하지 않는다.

## 급식 영역과 양식 모음

홈에 `오늘의 중식` 콜아웃과 양식 모음으로 가는 링크를 둔다. [MEALS.md](MEALS.md)의 전체 원본 검증을 마친 중식 메뉴·열량만 반영하며 최초 설치에는 연결 안내를 둔다. 학교·날짜·확인 시각·알레르기 번호·출처를 유지한다. 조식·석식·원산지·영양정보는 원본에 보존하고 홈에서 생략한다. 중식이 없으면 다른 식사로 대체하지 않으며 자료 없음·조회 오류를 구분한다. 기존 보관 기록은 바꾸지 않고 급식은 DB 행이나 일정으로 만들지 않는다.

[FORMS.md](FORMS.md)의 선택·모듈·담임 조건에 맞게 빈 양식 페이지를 만든다. 교사가 승인한 상담·학부모 연락·회의록·수업·평가·조회/종례 구조만 사용하고 실제 인물·기록을 예시로 넣지 않는다. 이는 복사용 페이지 양식이다. 실제 도구로 DB 네이티브 템플릿을 따로 등록하지 않았다면 새로 만들기 메뉴에 등록됐다고 보고하지 않는다.

기존 MCP 설치는 이미 있는 페이지·블록 ID를 확인하고 누락된 추가 영역만 만든다. Python `setup-extras`와 `meals-sync`는 완료된 Python 설치 상태를 사용하므로 MCP ID를 임의로 그 상태에 넣지 않는다. 생성 ID와 전용 급식 블록 소유 기록은 기존 MCP 설치 기록에 보관한다. 교사가 수정한 양식이나 다른 본문을 재설치로 덮어쓰지 않는다.

## 요청받은 매일 자동 갱신 등록

[CLOUD_SYNC.md](CLOUD_SYNC.md)에 따라 이미 만든 수첩을 운영자의 클라우드 서비스에 연결한다. 기본 제안은 Cloudflare 무료 플랜 시범 운영이다. 교사에게 같은 학교를 다시 입력하거나 NEIS 키를 발급받으라고 하지 않는다. 운영자 배포와 교사의 OAuth 승인은 MCP 설치 성공과 별개다.

1. 비공개 MCP 설치 기록과 기존 학교 설정에서 학교·학년도, 루트 페이지, 업무·일정 원본 data source, 급식 콜아웃을 찾는다. 현재도 활성 상태이고 실제 부모·스키마가 맞는지 읽어 확인한다. Cloudflare는 자식 없는 전용 콜아웃 외에 자체 본문은 비어 있고 자식 없는 활성 문단 하나만 가진 콜아웃도 지원한다. 문단의 부모가 해당 콜아웃과 일치하고 다른 자식·다음 조회 페이지가 없어야 한다. 조건에 맞으면 재사용하며 manifest에는 문단 ID가 아닌 바깥 콜아웃 ID를 기록한다. Firebase는 자식 없는 콜아웃만 지원한다. 기존 급식의 접기 블록·메모는 보존하고 필요하면 요청받은 전환 범위에서 새 전용 급식 콜아웃을 만든다. 연동 상태 전용 콜아웃이 없으면 수첩 안에 만들고 ID를 기록한다. 배포·링크 생성 명령이 기존 화면이나 설치 상태를 자동 변경하지는 않는다.
2. `CLOUD_SYNC.md`의 9개 필드만 포함한 manifest v1을 `.local/cloud-manifest.json`에 만든다. 원본 data source와 연결 DB·뷰 ID를 구분한다. 토큰·사용자 ID·학생 기록·전체 설치 JSON은 복사하지 않는다.
3. 운영자가 실제 배포한 서비스 주소가 있을 때 `python -m teacher_planner cloud-connect --manifest .local/cloud-manifest.json --service-url 'https://<실제_서비스_호스트>'`로 링크를 준비한다. 예시 호스트를 실제 연결로 안내하지 않는다. 이 명령은 링크를 만들 뿐 Notion이나 클라우드에 접속하거나 예약을 켜지 않는다.
4. 교사는 링크에서 학교와 연결 대상을 확인하고 Notion OAuth에서 **기존 교무수첩**을 선택한다. 새 템플릿을 복제하거나 MCP의 접근 토큰을 서비스에 전달하지 않는다. 선택한 상위 페이지의 하위 페이지 접근 범위도 안내한다.
5. 클라우드가 새 권한으로 대상·스키마를 검증하고, 실제 기존 NEIS 외부 ID·기간을 대조해 별도 실행 상태를 만든다. 활성 중복·모호한 기간은 자동 통합하지 않는다. MCP 설치 기록은 그대로 유지하며 Python 설치 상태를 가짜로 만들지 않는다.
6. 등록 활성 여부와 첫 동기화 성공·마지막 성공 시각을 각각 확인한다. 배포·OAuth·대상 검증이 남았다면 준비 중으로 보고한다. 기본 예약은 매일 오전 7시부터 한국 시간 기준 순차 실행이며 급식·학사일정만 대상이다.

## 중단·재실행

권한 부족·뷰 미지원·응답 유실 시 이미 만든 URL·ID를 보존하고 [RECOVERY.md](RECOVERY.md)를 따른다. 같은 섹션의 첫 뷰가 생성되었다면 후속 탭은 그 부모 DB를 재사용한다. 기존 DB를 삭제하거나 새 연결 블록을 반복해서 만드는 방식으로 실패를 숨기지 않는다.

새 버전은 새 설치 기본값이다. 이전 설치 상태를 삭제하거나 기존 수첩을 재설치하지 않는다. 요청받은 기존 수첩의 배치 수정은 [기존 수첩 배치 수정](UPDATES.md#기존-수첩을-공통-배치로-맞추기)을 따라 사전 구조를 저장하고 기존 ID·기록을 유지하는 이동·너비·접기 변경만 진행한다. 실제 생성·검증한 내용과 미리보기·모의 테스트를 구분해 최종 보고한다.
