# 설치 또는 가져오기 중단 후 복구

## 정상 재실행

같은 config, parent, state를 사용한다. 생성된 ID가 `.local/state.json`에 있어 DB·페이지·뷰를 재사용한다. 관계 속성은 존재 여부와 대상을 확인한 후 누락분만 추가한다. 사용자가 바꾼 기존 뷰는 설치 재실행으로 덮어쓰지 않는다. `verify`로 차이를 확인한다.

state는 수첩 하나의 설치 기록이다. 삭제하거나 Git에 올리지 않는다. 다른 컴퓨터로 옮길 때는 개인 저장소 밖의 안전한 경로로 config와 state를 함께 옮긴다. 토큰은 별도로 새 환경에 설정한다. 동시에 같은 수첩을 변경하지 않는다.

## 400 / 401 / 403 / 404 / 429

이 응답은 생성이 거부된 것으로 처리한다. 오류 원인(속성·토큰·권한·부모 공유)을 해결하고 같은 명령으로 이어간다. 429는 Retry-After를 따르며 제한된 횟수만 재시도한다. 긴 대기는 사용자에게 재실행을 안내한다.

## 타임아웃 / 5xx / 응답 유실

생성 요청을 자동 재시도하면 중복될 수 있다. 도구는 쓰기 전에 `pending`을 저장하고 성공 응답과 ID를 저장한 뒤 해제한다. 생성 결과가 불확실하면 다음 실행을 막는다.

1. `.local/state.json`의 `pending.key`, `endpoint`, `payload`를 로컬에서 확인한다. payload에 기록 내용이 있을 수 있으므로 공개하지 않는다.
2. 지정한 부모에서 해당 제목/뷰가 생성되었는지 Notion으로 확인한다.
3. 이미 생성되었으면 반환 객체의 UUID로 연결한다.

```bash
python -m teacher_planner recover --id 실제_객체_UUID
```

도구는 연결 계정과 제목·부모 또는 뷰 종류·원본을 검사한다. 페이지 레이아웃 블록은 부모·유형·내용과 하위 블록 구조까지 검사한다. 완료 후 원래 명령을 재실행한다.

**각 섹션에서 `create_database`로 만든 첫 연결 뷰**는 새 데이터베이스 컨테이너까지 생성하기 때문에 자동 recover가 거부된다. 주간 캘린더를 처음 만드는 요청도 여기에 해당한다. AI는 뷰를 fetch하고 그 부모 데이터베이스의 부모 페이지가 `pending.payload.create_database.parent.page_id`와 일치하는지, 이름·종류·data source ID도 일치하는지 확인한다. 일치하면 state의 `objects[pending.key]`에 `{id, object, parent, type, name}`을 기록하고 `pending`만 제거한다. 다른 기록은 보존한다.

**같은 섹션의 연결 DB에 추가하는 후속 탭**은 `database_id`를 사용하는 뷰 생성 요청이다. 생성된 뷰의 UUID로 `recover`를 실행하면 기존 부모 DB·원본·이름·종류를 검증한다. 첫 뷰가 성공했다면 저장된 첫 뷰의 `parent.database_id`를 재사용한다. 예를 들어 주간 캘린더 다음 월간·마감 탭, 학생 명렬표 다음 갤러리·관찰 탭, 진도의 반별 보기 다음 교과·학기별 탭이 여기에 해당한다. 첫 뷰나 별도 연결 DB를 다시 만들지 않는다. 각 섹션의 탭들이 같은 부모 DB와 원본을 사용하는지 확인한 뒤 원래 명령을 이어간다. 서로 다른 페이지의 동명 섹션은 각자의 부모 DB를 사용한다.

**아무 객체도 생성되지 않았음이 확인된 경우에만** state를 비공개 위치에 백업하고 `pending` 필드만 지운 뒤 재실행한다. 확인되지 않으면 pending을 지우거나 state 전체를 초기화하지 않는다.

기존 행이나 블록의 명시 속성을 갱신하는 PATCH는 같은 입력으로 재실행할 수 있다. **블록 자식 추가(`PATCH /blocks/{id}/children`)는 새 객체를 만드는 작업**이므로 일반 생성과 똑같이 저널과 `pending`을 사용한다. 오류가 났다고 이 요청을 임의로 반복하지 않는다.

시간표·주간 격자 갱신 사이에 끊겼다면 같은 입력으로 다시 실행한다. 시간표 행을 먼저 맞춘 다음 그 주의 저장된 수업을 읽어 저장된 격자 ID로 주간표를 갱신한다. 버전 3의 격자는 교과 페이지에 있고, 이전 설치의 격자는 원래 위치를 유지한다. 원본에서 빠진 수업은 기존 보존 규칙을 유지한다. Notion API는 이 여러 행·블록에 대한 트랜잭션을 제공하지 않는다.

## 이전 시간표 복사 일정

현재 시간표 가져오기는 교사 시간표와 표시용 격자만 갱신한다. 홈의 오늘 수업은 같은 시간표 원본을 읽는다. 업무·일정 행이나 시간표의 `업무·일정` 관계를 만들거나 수리하지 않는다.

이전 버전에서 만든 업무·일정 복사본과 관계는 자동 수정·취소·삭제하지 않는다. 남아 있는 복사본을 가져오기 실패로 보고 반복 생성하거나 상태를 초기화하지 않는다. 정리가 필요하면 대상 행의 외부 ID·기간·교사와 유지할 수동 기록을 확인한 별도 작업으로 처리한다.

## NEIS 학사일정 반영 중단

학교·학년도·기간을 검증한 조회가 성공한 뒤 기존 업무·일정 원본에 반영한다. API 오류나 일부 페이지만 받은 결과를 빈 일정으로 적용하지 않는다. 정상 0건 결과도 기존 행사를 지우는 명령이 아니다.

일정 페이지 생성이나 연동 전용 콜아웃 추가 도중 응답이 유실되면 위 생성 복구 절차를 따른다. 같은 외부 식별값의 일정과 전용 블록이 이미 있는지 확인하고 기존 `pending`·페이지 ID·블록 소유 기록을 유지한다. 연동이 관리하는 이름·일정과 기존 전용 콜아웃의 갱신은 같은 입력으로 재실행하되 교사가 쓴 다른 본문을 재생성하지 않는다.

`neis_source`는 첫 반영의 교육청·학교·학년도를 연결하는 로컬 상태다. 대상이 달라 중단되면 학교 코드·config·state 경로를 확인하고 기존 연결을 임의 초기화하지 않는다. `neis_last_checked_at`·`neis_last_range`는 마지막 확인 시각·범위이며 공용 설정이나 Git에 넣지 않는다.

날짜·행사명 변경으로 새 기록이 생기거나 원본에서 이전 행사가 사라진 것은 생성 실패로 보지 않는다. 이전 행사의 보관·취소 여부는 실제 원본과 비교해 결정한다. 동기화가 임의로 삭제·취소하지 않는다. 전체 동작은 [SCHOOL_CALENDAR.md](SCHOOL_CALENDAR.md)를 참고한다.

## 프로세스 강제 종료

정상 종료 시 `.local/state.lock`은 제거된다. 강제 종료로 남았으면 **실행 중인 설치/가져오기 프로세스가 없는지 확인한 후** 해당 lock 파일만 제거한다. 이 잠금은 같은 컴퓨터·state 경로만 보호한다. 다른 컴퓨터나 MCP 작업과의 동시 실행은 피한다.

## 설계 버전이 달라진 경우

버전 3의 네 페이지 배치는 새 설치 기본값이다. 이전 상태를 새 설계의 `install`에 사용하면 서명 차이로 중단하며 기존 페이지를 자동 재구성하지 않는다. 새 수첩이 필요하면 별도 상태 경로를 사용하고, 기존 상태·기록·격자 ID는 보존한다. 설계 차이를 응답 유실로 취급해 `pending`을 지우거나 상태를 초기화하지 않는다.

## 지원하지 않는 복구

삭제된 DB 재구성, 관계를 다른 DB로 교체, 기존 수첩 자동 마이그레이션, 누락된 시간표의 자동 삭제는 수행하지 않는다. 사용자의 원래 데이터를 확인한 후 별도 작업으로 처리한다.
