# 기능을 고르고 관계와 보기를 함께 만들기

[기능 선택과 예시](https://notion-teacher-planner.notion-teacher-planner-cloudflare.workers.dev/features)에서 어떤 기록을 연결할지 먼저 확인한다. 기능을 누르면 가상 학생·학급·업무로 만든 예시와 사용 흐름을 볼 수 있다. 화면의 선택은 AI에게 전달할 요청문을 준비하는 단계이며, 실제 Notion을 읽거나 수정하지 않는다.

관계는 원본 기록끼리 연결하고, 보기는 현재 학생·학급·프로젝트에 해당하는 기록을 보여 준다. 예를 들어 상담에 학생을 선택한 뒤 그 학생 페이지에서 같은 상담을 여는 구조다. 제목에 학생 이름을 적거나 관계 속성만 만들어 둔 상태와 구분한다.

## 세 가지 시작 방식

| 선택 | 포함하는 기능 | 필요한 선택 모듈 |
| --- | --- | --- |
| 기본 설정 (`basic`) | ① 학생별 기록, ② 학급별 공간, ③ 시간표·진도·자료 연결 | 추가 모듈을 자동으로 켜지 않음 |
| 추천 설정 (`recommended`) | 기본 설정 + ④ 후속 업무, ⑤ PARA 프로젝트, ⑥ 제출물 수합, ⑦ 평가 범위 | 출결·제출물, 평가·채점, 학부모 연락, 회의록을 포함하는 선택임을 표시 |
| 커스텀 (`custom`) | ①~⑨에서 필요한 기능만 선택. 모두 또는 없음도 가능 | 선택한 기능의 필수 모듈을 함께 확인 |

모든 기능을 사용할 수 있지만 처음부터 전부 켜지 않는다. 추천은 선택지이며 교사의 응답을 대신하지 않는다. 첫 다섯 기능만 개별 선택한 경우 학부모 연락·회의 등 미선택 모듈을 추가하지 않는다. 해당 모듈이 이미 켜져 있을 때 관련 연결을 포함한다. 프리셋에서 개별 기능을 바꾸면 최종 선택을 `커스텀`으로 기록한다. 다른 프리셋으로 바꾸어도 교사가 이미 고른 추가 모듈을 자동으로 끄지 않으며 최종 모듈 목록을 확인한다.

## 9개 기능과 실제 사용 모습

| 번호·기능 키 | 연결과 사용할 보기 | 기록을 어떻게 남기나 | 필요한 범위 |
| --- | --- | --- | --- |
| ① 학생별 기록 모아 보기 · `student_history` | 학생에서 **상담 이력 / 연락 이력 / 출결 기록 / 미제출** 확인 | 상담·연락·출결·제출 기록에 학생을 선택. 같은 원본을 학생 페이지에서 최신순으로 확인 | 상담 연결은 기본 설계에 존재. 연락·출결·제출물은 해당 모듈을 선택했을 때만 포함 |
| ② 학급별 업무 모아 보기 · `class_hub` | 학급에서 **명렬표 / 수업 진도 / 시간표 / 평가** 확인 | 담당 반에 연결된 기존 학생·진도·수업·평가를 모아 봄 | 기존 학급 원본 재사용. 평가는 모듈 선택 시 포함 |
| ③ 시간표·진도·자료 연결 · `lesson_links` | 단원에서 **연결 수업 / 수업 자료** 확인 | ‘파동’ 단원에 실제 수업일·교시와 학습지를 연결 | 기존 진도·시간표·자료 관계 재사용. 수업을 To-Do로 복사하지 않음 |
| ④ 상담·회의 후속 업무 연결 · `followups` | 상담·연락·회의에서 **미완료 후속 업무**, 할 일에서 **관련 원본 기록** 확인 | 상담 뒤 확인할 일이나 회의 결정의 실행 업무를 한 번 등록하고 연결 | 상담은 기본. 연락·회의는 선택한 모듈에 한함 |
| ⑤ PARA 관련 기록 모아 보기 · `para_hub` | 프로젝트에서 **관련 업무 / 회의 / 자료**, 담당 영역에서 관련 프로젝트 확인 | ‘학부모 총회’ 프로젝트에 준비 업무·회의록·안내문을 연결 | 기존 PARA 원본 재사용. 회의는 모듈 선택 시 포함 |
| ⑥ 제출 항목별 현황 관리 · `submissions` | 제출 항목에서 **미제출 / 보완 요청 / 제출 현황**, 학생에서 해당 제출 기록 확인 | ‘동의서’ 항목 1건과 **학생 1명 × 제출 항목 1개**의 체크 기록을 분리 | 출결·제출물 모듈 필요. **제출 항목 DB** 추가 |
| ⑦ 평가 범위·수업 진도 연결 · `assessment_scope` | 평가에서 **대상 단원 / 채점 기준표**, 단원에서 관련 평가 확인 | 평가 한 건에 여러 단원과 기준표 자료를 연결 | 평가·채점 모듈 필요. 평가↔진도 관계 추가 |
| ⑧ 학생별 평가 결과 기록 · `assessment_results` | 평가에서 **학생별 채점·피드백**, 학생에서 자신의 평가 결과 확인 | **학생 1명 × 평가 1건**을 별도 결과 행으로 기록 | 평가·채점 모듈 필요. **학생별 평가 결과 DB** 추가. 기본·추천에는 미포함 |
| ⑨ 담당 교직원 연결 · `staff_links` | 업무·회의·계정에서 담당 교직원의 연락망을 열고 교직원에서 관련 업무 확인 | 담당자 이름을 반복 입력하는 대신 실제 연락망의 사람을 선택 | 교직원 연락망 모듈 필요. 회의·학교 계정 연결은 해당 모듈도 켠 경우만 포함 |

예시는 동작 설명용 가상 자료다. 웹의 가상 사례를 설치 기록으로 자동 복사하지 않는다. 실제 수첩에 데모를 넣는 선택은 별도 질문 Q09로 받는다. 제출·채점 결과가 없는 학생의 상태를 추정하거나 기록을 임의 생성하지 않는다.

## 입력 설정과 호환성

선택 원본은 [`workflow_catalog.json`](../teacher_planner/workflow_catalog.json) 버전 1의 기능 목록이며 설치 설정의 선택 항목 `workflows`로 전달한다. 기본 설정 예시는 다음과 같다.

```json
{
  "workflows": {
    "preset": "basic",
    "features": ["student_history", "class_hub", "lesson_links"]
  }
}
```

추천 설정의 기능은 앞의 일곱 키이며, 필요한 `modules.attendance`, `modules.assessment`, `modules.contact`, `modules.meeting`도 선택 요약에 명시한다. 커스텀에서는 프리셋 이름과 선택 배열을 함께 저장한다. `submissions`에는 `attendance`, `assessment_scope`·`assessment_results`에는 `assessment`, `staff_links`에는 `staff`가 필요하다. 불일치는 생성 전에 해결하며, 이미 받은 답을 조용히 바꾸지 않는다.

**이전 설정에 `workflows`가 없으면 이전 설치 의미를 그대로 유지한다.** 기본 설정을 몰래 추가하거나 과거 config·state·설계 파일을 새 버전으로 덮어쓰지 않는다. 명시적인 기능 없음은 `{"preset":"custom","features":[]}`로 표현한다. 기존에 설치된 관계를 제거하라는 뜻은 아니다.

웹 질문지의 Q05는 어떤 기록 DB를 쓸지, Q05W는 어떤 연결과 상세 보기를 쓸지 정한다. 웹 답변이 있으면 재질문하지 않고 그대로 전달한다. 미리보기 설계 버전 4는 선택한 `workflows`도 포함하며, 버전 1~3은 각 버전의 원래 규칙으로 검증한다. 버전 숫자만 바꿔 새 기능을 끼워 넣지 않는다.

## AI가 설치할 때

로컬 실행이 가능하면 다음 명령으로 선택한 기능의 스키마와 상세 보기 계획을 먼저 확인한다.

```sh
python -m teacher_planner workflow-plan --config .local/config.json
```

이 명령은 **계획 생성**이며 Notion 쓰기나 설치 완료 검증을 수행하지 않는다. 계획에 있는 관계 대상·역관계·필터·정렬·표시 항목을 실제 도구와 원본 ID에 맞추어 구성한다. 새 설치에서는 선택된 기능의 스키마를 함께 만들고, 공통 상세 페이지 보기는 지원되는 MCP/UI에서 마무리한다. 구체적인 절차는 [MCP 설치](INSTALL_WITH_MCP.md#선택한-기능의-관계와-상세-보기)와 [완료 검사](ACCEPTANCE.md#선택한-기능의-관계와-상세-보기)를 따른다.

학생·학급·프로젝트 상세 페이지의 필터는 **현재 열린 페이지와의 관계**를 사용한다. 고정된 예시 학생이나 학급 하나를 모든 템플릿에 넣지 않는다. 기존 양방향 관계는 재사용하고 같은 이름의 별도 관계를 중복 생성하지 않는다. 도구가 지원하지 않는 상세 레이아웃은 UI로 마무리하거나 정확한 대기 항목으로 남긴다. 스키마가 생성되었다고 실제 관계 보기까지 완료했다고 보고하지 않는다.

관계만 연결해도 일정·마감·성적·완료 상태가 자동 복사되지는 않는다. To-Do가 필요하면 업무·일정 원본에 한 행을 만들고 연결한다. 주간·월간은 같은 일정 원본을 유지하며, 시간표의 수업을 할 일·학사 캘린더에 복사하지 않는다. 출결 당시의 학급은 학생의 현재 학급과 별도로 보존한다.

제출 현황은 대상 학생과 학생별 제출 기록이 갖춰졌는지 확인한 뒤 집계한다. 기록이 없다는 이유로 제출 완료로 계산하지 않는다. 대상 학생과 대상 확정일을 별도로 기록하고, 항목 ID와 학생 ID로 만든 `기록 키`로 중복을 확인한다. 평가 결과는 평가별 총괄 채점 숫자와 개인별 결과를 구분하며, 실제로 구성·검증한 집계만 안내한다. ⑧을 선택했다는 이유로 학생별 점수나 피드백을 만들어 채우지 않는다. 미채점·결시는 점수 0이 아닌 빈칸으로 구분하고 실제 채점 점수는 평가의 만점 범위 안에서 입력한다. 평가 ID와 학생 ID로 `기록 키`를 기록해 같은 학생·평가의 중복 결과를 막는다. 현재 계획은 필터 보기와 확정된 대상 명단 대조를 사용하며 자동 롤업을 설치한 것으로 설명하지 않는다. 기존 평가의 대상 인원·채점 완료·채점률은 자동으로 덮어쓰지 않는다.

## 실제 상세 보기의 증거 검사

설치 담당 AI가 실제 Notion의 상세 보기와 화면을 다시 확인한 뒤 다음 명령으로 수집한 증거를 검사할 수 있다.

```sh
python -m teacher_planner verify-workflows --config .local/config.json --snapshot .local/workflow-snapshot.json
```

증거에는 계획의 `plan_digest`, DB 키별 실제 원본 ID인 `data_sources`, 상세 페이지를 제공하는 DB별 실제 전체 기록 수인 `host_record_counts`, 실제 보기의 `views`를 넣는다. `host_record_counts`는 전체 조회로 확인한 0 이상의 정수다. 해당 DB에 기록이 2개 이상 있으면 각 상세 보기와 집계에 서로 다른 현재 페이지 2개의 증거를 요구한다. 기록이 정확히 1개라면 그 1개를 확인하고, 0개거나 전체 수를 확인하지 못했다면 확인 대기(`pending`)로 남긴다. 검사를 통과시키려고 실제 수를 줄여 쓰거나 가상 기록을 임의 추가하지 않는다.

각 보기에는 대응하는 `plan_key`, `current_page_id`, `host_data_source_id`, `parent_page_id`, `data_source_id`, `type`, 실제 현재 페이지 ID로 해석된 `filter`, `sorts`, `visible_properties`, 실제로 확인한 `ui_checked`·`new_record_checked`가 필요하다. 같은 페이지를 두 번 넣는 것으로 서로 다른 대상 검사를 대신할 수 없다.

계획에 `record_rules`나 `counters`가 있으면 다음 증거도 필요하다. 보기의 관계 필터·화면이 맞다는 사실만으로 중복 방지나 제출·채점률까지 검증된 것은 아니다.

| 증거 항목 | 담을 내용 |
| --- | --- |
| `record_rule_checks` | 원본마다 검사 1건. `source`, `data_source_id`, 계획의 해당 `rule`, 양의 정수인 `checked_record_count`, 실제 규칙 위반 목록 `violations`, `readback_checked`, `new_record_checked`, `legacy_rows_preserved` |
| `counter_checks` | 검사한 상세 페이지마다 1건. `host`, `current_page_id`, `host_data_source_id`, `source_data_source_id`, 계획의 해당 `counter`, `target_student_ids`, `completed_student_ids`, `missing_student_ids`, `duplicate_record_keys`, `roster_confirmed`, `displayed`, `readback_checked`, `ui_checked`, `includes_unrecorded_students` |

기록 규칙은 학생과 항목/평가의 관계가 각각 정확히 하나인지, `기록 키`에 중복이 없는지, 기존 기록이 보존됐는지 실제로 확인한다. 평가 결과에서는 미채점·결시의 빈 점수와 채점 점수의 만점 범위도 검사한다. 실제 검사 후 `violations=[]`이며 각 확인 항목이 참이어야 한다. 확인한 기록이 없거나 필요한 확인 항목이 빠지면 대기 상태다.

집계의 세 학생 ID 목록은 중복 없는 실제 ID 배열이다. 완료자는 대상자의 부분집합이며, 미완료자는 **대상자에서 완료자를 뺀 전체**다. 제출·평가 결과 행이 아직 없는 대상 학생도 미완료 목록에 포함한다. `duplicate_record_keys=[]`를 확인하고 `displayed`의 `denominator`는 대상 인원, `numerator`는 완료 인원과 대조한다. `percentage`는 대상이 확정되고 분모가 0보다 클 때 `round(100 × 완료 인원 / 대상 인원, 1)`이며, 대상 미확정·분모 0은 숫자 0이나 100 대신 `미설정`으로 표시한다. 실제 원본·화면·미기록 학생까지 확인한 뒤 해당 확인 항목을 참으로 기록한다.

검사할 `rule`·`counter`는 계획과 정확히 같아야 한다. 검사 결과와 ID·명단·인원수는 계획에서 복사해 성공 표시를 만드는 용도가 아니라 **실제 조회·화면 확인 결과**로 채운다. 필요한 규칙·집계 증거가 없으면 `evidence_valid=false`와 대기 항목을 유지하며 설치 완료로 표시하지 않는다.

Python 전체 설치의 마지막 `verify`에는 기존 배치 증거와 함께 `--workflow-snapshot .local/workflow-snapshot.json`을 전달한다. **`verify-workflows` 자체는 Notion을 조회하지 않는다.** 전달받은 증거가 계획과 맞는지만 검사하며 `applied=false`, `live_notion_verified=false`를 유지한다. 실제 확인을 대신하지 않으며 전체 기록 수와 학생·학급 등 서로 다른 대상을 구분해 확인한 근거는 비공개 작업 기록에도 남긴다. 스키마만 확인된 빈 수첩은 상세 보기·기록 규칙·집계의 실제 확인을 대기 상태로 인계한다.

## 이미 쓰는 수첩에 추가하기

[기능 선택 화면](https://notion-teacher-planner.notion-teacher-planner-cloudflare.workers.dev/features) 또는 [수정 요청문 화면](https://notion-teacher-planner.notion-teacher-planner-cloudflare.workers.dev/edit)에서 필요한 기능을 고르고 **본인의 기존 수첩**을 대상으로 요청한다. 새 설치를 다시 진행하지 않는다.

AI는 먼저 기존 DB·페이지·data source·관계 속성·보기 ID와 기록 수를 확인한다. 이미 있는 기능은 검증·보완하고 없는 속성·보기만 추가한다. 새 제출 항목이나 평가 결과 DB가 필요한 경우에도 기존 제출·평가 원본은 보존한다. 현재의 텍스트 항목을 같은 이름이라는 이유만으로 임의 통합하지 않으며, 학생별 기존 기록의 정확한 대상을 확인한다. 기존 단방향 관계 변경은 [관계 보존 절차](UPDATES.md)를 따른다.

원래 config와 설치 상태는 유지하고 선택 변경·실제 적용 ID·검증 결과를 별도 비공개 기록으로 남긴다. 공개 공유받은 다른 교사의 후기 페이지는 참고 자료이며, 그 페이지를 수정하거나 실제 기록을 복제하는 권한을 뜻하지 않는다. 기능 선택·요청문 생성·Git 배포로 기존 사용자의 Notion이 자동 변경되지는 않는다.
